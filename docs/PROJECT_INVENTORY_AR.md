# مرجع مشروع WeCare

آخر مراجعة: 15 أغسطس 2026  
الفرع المرجعي: `Dashboard_modifications`

## 1. تعريف النظام

WeCare نظام لإدارة مركز صحي، ويتكون من:

- لوحة ويب للعاملين والمرضى.
- API لتطبيق الهاتف باستخدام Laravel Passport.
- إدارة المرضى والأطباء والعيادات والمواعيد والزيارات والملفات الطبية.
- أسئلة المرضى والإجابات الطبية.
- تقارير تشغيلية وتحليل جغرافي لانتشار الأمراض.
- محافظ مالية وإعلانات وتقييمات مجمعة للأطباء.

## 2. التقنية والبنية

- PHP 8.1 أو أحدث.
- Laravel 10.
- MySQL عبر XAMPP هو مصدر البيانات الفعلي.
- لا يعتمد تشغيل المشروع على migrations الموجودة في `database/`، ولا تُنشأ الجداول منها.
- Laravel Passport لمصادقة API.
- Spatie Laravel Permission للأدوار والصلاحيات.
- Blade + Bootstrap + واجهة RTL عربية موحدة.
- Leaflet لخرائط تحليل الأمراض.
- GeoJSON محلي لحدود محافظات سورية الأربع عشرة في `public/assets/data/syria-governorates.geojson`.
- نمط Repository مستخدم في أجزاء المرضى والأطباء والعيادات والمواعيد والأسئلة والإعلانات والمحافظ والملف الطبي.

## 3. أنواع المستخدمين المعتمدة

| النوع الموحد | الأسماء القديمة المقبولة | الاستخدام |
|---|---|---|
| `super_admin` | admin, administrator, مدير | إدارة النظام والمركز بالكامل |
| `secretary` | reception, receptionist, استقبال, سكرتير | التشغيل اليومي والاستقبال |
| `doctor` | طبيب | المواعيد والمرضى والملفات والأسئلة الخاصة به |
| `patient` | user, مريض, مستخدم | حساب المريض وخدمات التطبيق |

تتم مطابقة الأسماء القديمة في `App\Models\User::canonicalRoleName()`.

## 4. التسجيل والمصادقة

- تسجيل الدخول للوحة الويب فعال.
- إنشاء حساب عام من لوحة الويب معطل عمدًا.
- حسابات الموظفين والأطباء ينشئها المدير.
- تسجيل مريض جديد من التطبيق ما زال فعالًا عبر `POST api/register`.
- API يستخدم `auth:api` وPassport.
- توجد حدود طلبات على تسجيل الدخول والتسجيل والتحقق وبعض إجراءات المواعيد.
- التحقق من البريد وإعادة إرسال رمز التحقق موجودان في API.

## 5. لوحات التحكم

### المدير والسكرتارية

- إجمالي المرضى.
- الأطباء النشطون.
- مواعيد اليوم والمواعيد المعلقة والمكتملة.
- إجمالي الزيارات.
- نشاط المواعيد خلال سبعة أيام.
- مواعيد اليوم والمرضى المضافون حديثًا.

### الطبيب

- مواعيد اليوم والقادمة.
- المرضى المرتبطون بمواعيده.
- زياراته الطبية.
- الأسئلة التي تنتظر إجابته.
- نشاط مواعيده خلال سبعة أيام.

### المريض

- المواعيد القادمة والمكتملة.
- عدد الزيارات.
- عدد الأسئلة.
- أقرب المواعيد الخاصة به.

## 6. إدارات لوحة الويب

### إدارة الرعاية

- المرضى: قائمة، بحث، إضافة، تعديل، ملف المريض، المواعيد والزيارات.
- الأطباء: قائمة، إضافة، تعديل، حالة الدوام، الاختصاص، أيام وساعات العمل والتقييم المجمع.
- العيادات والأقسام: إدارة الأقسام وربط الأطباء والخدمات بها.
- المواعيد: إنشاء، تصفية، مواعيد اليوم والقادمة والمعلقة، تأكيد وإلغاء.
- الزيارات: زيارة المريض، التكلفة، الطبيب، العيادة والتاريخ.
- زيارات الطبيب وإيراداته: تصفية بالشهر أو اليوم أو بين تاريخين وإجمالي التكلفة المعروضة.

### الملف الطبي

- صفحة مستقلة للبحث عن ملفات الزيارات وفتحها.
- التاريخ الطبي والسوابق.
- الشكاوى.
- الفحص السريري.
- الاستقصاءات/الإجراءات.
- الملاحظات.
- معلومات المريض الطبية.
- الخدمات الطبية المقدمة.
- التشخيص النصي القديم.
- تشخيص ICD-10 المستخدم في التحليلات.
- الكتابة السريرية مقيدة بالطبيب المرتبط بالمريض من خلال موعد.

### التواصل

- جميع أسئلة المرضى للإدارة.
- أسئلة عيادة الطبيب.
- قائمة مستقلة للأسئلة التي تنتظر إجابة الطبيب مع عداد في القائمة.
- أسئلة المستخدم نفسه.
- إضافة سؤال وتسجيل أو تعديل الإجابة حسب الصلاحية.

### التشغيل والتقارير

- المحافظ: سجل الحركات، إجمالي الإضافات والسحوبات؛ واجهة الويب الحالية للعرض فقط.
- التقارير: المرضى والزيارات والمواعيد، أهم العيادات والتشخيصات والزيارات الحديثة، وتصدير CSV.
- الإعلانات: إنشاء وتعديل وتفعيل وحذف إعلانات تطبيق المرضى؛ ظاهرة لمدير النظام فقط.
- تقييمات الأطباء: عدد التقييمات ومتوسط كل طبيب. قاعدة البيانات تحفظ حاليًا قيمة مجمعة ولا تحفظ نص كل مراجعة كسجل مستقل.

### إدارة النظام

- المستخدمون.
- الأدوار والصلاحيات.
- الإدارة متاحة لمدير النظام فقط.

## 7. تحليل الأمراض

- يعتمد على تشخيصات ICD-10 المسجلة في ملفات الزيارات وبيانات موقع المريض.
- الفلاتر: المرض، المحافظة، المنطقة، الجنس، العمر، من تاريخ، إلى تاريخ.
- يحسب المرضى الفريدين وسجلات التشخيص والمحافظات المتأثرة ونسبة الانتشار.
- توزيع حسب المحافظة والمنطقة والعمر والجنس والزمن.
- مقارنة بالفترة السابقة عند تحديد نطاق زمني.
- مؤشرات جودة البيانات وترميز ICD-10.
- تصدير النتائج إلى CSV.
- خريطة دوائر انتشار على OpenStreetMap.
- خريطة Choropleth لونية بحدود محافظات سورية.
- عرض سورية كاملة أو محافظة مختارة.
- لوحة تفاصيل للمحافظة: العدد، المعدل لكل 1000، الحصة، الترتيب، المناطق الأعلى، العمر، الجنس والمقارنة السابقة.
- إمكانية تطبيق المحافظة المختارة كفلتر على كامل الصفحة.
- إخفاء الأرقام الدقيقة الأقل من خمسة في الواجهة والتصدير لحماية الخصوصية.

## 8. خدمات تطبيق الهاتف عبر API

يوجد حاليًا 36 مسار API، وأهم الخدمات هي:

- تسجيل المريض وتسجيل الدخول والخروج والتحقق من البريد والملف الشخصي.
- المحافظات والمناطق والجنسيات والعيادات.
- الأقسام والأطباء المشهورون والبحث عن طبيب والأطباء حسب القسم.
- أيام الطبيب المتاحة والفترات الزمنية والأوقات المحجوزة.
- إنشاء الموعد وتعديله وإلغاؤه وحذفه.
- مواعيد المريض السابقة والملغاة والقادمة.
- مواعيد الطبيب ومواعيد اليوم وقبول أو رفض الموعد.
- زيارات المريض والبيانات الطبية للزيارة.
- إضافة تقييم للطبيب.
- إرسال سؤال، أسئلة المريض، أسئلة الطبيب وتسجيل الإجابة.

## 9. الصلاحيات والحماية الحالية

- Policies موجودة للمريض والموعد والزيارة والسؤال.
- `RequireStaff` يحصر الصفحات التشغيلية في المدير والسكرتارية.
- `AuthorizeMedicalVisit` يقيد تعديل عناصر الملف الطبي بالطبيب المرتبط بالزيارة.
- الإعلانات والتقييمات الإدارية مقيدة بـ `super_admin`.
- المستخدم العادي لا يرى قوائم الإدارة.
- الطبيب يرى مرضاه ومواعيده وزياراته وملفاتهم وأسئلة اختصاصه.
- المريض يرى بياناته الشخصية في لوحة الويب، ويستخدم الخدمات الكاملة عبر التطبيق.
- CSRF فعال لمسارات الويب، ومصادقة Passport فعالة لمسارات API المحمية.

## 10. حالة التصميم

- تصميم WeCare موحد وRTL للوحة التحكم والصفحات الأساسية.
- القائمة الجانبية تتغير حسب نوع المستخدم.
- توجد مكونات Blade موحدة للرؤوس والأزرار والتنبيهات والحالات الفارغة والجداول.
- صفحات المرضى والأطباء والأقسام والمواعيد والتقارير والإعلانات والتحليلات والأسئلة والبروفايل أعيد تصميمها.
- ما زالت بعض صفحات الملف الطبي والزيارات والنماذج الفرعية تستخدم تصميم Valex القديم وتحتاج توحيدًا لاحقًا.
- ما زالت صفحات Valex التجريبية موجودة كملفات، لكنها غير معروضة في القائمة الأساسية.

## 11. ميزات غير متوفرة فعليًا حتى الآن

- الاستشارة المرئية VideoCall غير منفذة؛ الموجود في القالب أيقونات وصفحات تجريبية فقط.
- لا يوجد نظام جلسة فيديو أو غرفة أو مزود WebRTC أو سجل مكالمات طبي حقيقي.
- لا يوجد Drill-down بحدود جغرافية فعلية لمناطق المحافظة؛ المتاح حاليًا حدود المحافظات ADM1 وقائمة المناطق النصية.
- التقييمات محفوظة بصورة مجمعة على الطبيب، وليست مراجعات مستقلة قابلة للتدقيق.
- لا يوجد سجل تدقيق Audit Log شامل للعمليات الحساسة.
- لا يوجد نظام إشعارات موحد داخل اللوحة للمواعيد والأسئلة.
- إدارة دفع إلكتروني حقيقية غير موجودة؛ المحافظ الحالية سجل داخلي فقط.

## 12. ديون وأخطاء تقنية معروفة

1. `Cln_m_servicesController::index()` يحتوي `dd($allvisit)`، لكن مسار index أزيل من الويب واستبدل بصفحة الملفات الطبية الجديدة.
2. توجد عدة دوال Resource فارغة أو قديمة في Controllers وRepositories وينبغي حذفها أو إكمالها.
3. `QuestionsRepository::destroy()` يحتوي منطقًا قديمًا خاطئًا خاصًا بالإعلانات، بينما Controller يتجاوز هذا المنطق ويحذف نموذج السؤال مباشرة.
4. بعض الاستعلامات القديمة تبني SQL للتواريخ باستخدام النص وتحتاج إعادة كتابة آمنة وموحدة.
5. يوجد مسار Catch-all قديم لصفحات القالب، لكنه محمي بـ `staff`؛ الأفضل حذفه بعد التأكد من الصفحات المطلوبة.
6. المسار القديم `fix-password` معطل برمجيًا بواسطة `if (false)`؛ الأفضل حذفه نهائيًا.
7. توجد ازدواجية لمسار `api/departments` في `routes/api.php`؛ آخر تعريف هو المستخدم فعليًا.
8. اختبارات Laravel الافتراضية غير متوافقة مع المشروع: `UserFactory` غير موجود وبعض الاختبارات تتوقع التسجيل العام المعطل عمدًا.
9. لا توجد تغطية اختبارات للمرضى والمواعيد والملف الطبي والصلاحيات وAPI والتحليلات.
10. ملفات رفع الصور القديمة تستخدم حذف ملفات مباشرًا وتحتاج توحيدًا عبر Storage والتحقق من المسار.
11. بعض أسماء الجداول والموديلات قديمة وغير متناسقة (`cln_*`, `gnr_*`, `statue`, `mounth`) ولا ينبغي تغييرها قبل وضع طبقة توافق مع قاعدة XAMPP الحالية.
12. توجد ملفات crash وملفات غريبة في جذر المشروع ينبغي تنظيفها بعد أخذ نسخة احتياطية والتأكد أنها غير مستخدمة.

## 13. الاختبارات والتحقق

- فحص بناء PHP للمكونات المعدلة ناجح.
- تجميع قوالب Blade ناجح.
- فحص المسارات ناجح.
- الاختبارات الحالية: ثلاثة اختبارات تمر، والبقية قديمة أو متوقفة بسبب غياب `Database\Factories\UserFactory` وتوقعات التسجيل العام.
- لا ينبغي تشغيل migrations على قاعدة XAMPP الفعلية.

## 14. أولويات التطوير التالية

1. إضافة اختبارات صلاحيات وتدفقات حرجة دون الاعتماد على قاعدة الإنتاج.
2. توحيد تصميم صفحات الملف الطبي والزيارات الفرعية.
3. تنظيف المسارات والدوال القديمة وCatch-all وصفحات Valex غير المستخدمة.
4. فصل المراجعات إلى سجلات مستقلة مع المريض والطبيب والتاريخ والتعليق.
5. إضافة إشعارات للأسئلة والمواعيد.
6. تنفيذ VideoCall فقط بعد تحديد المزود وسياسة الخصوصية والموافقة الطبية.
7. إضافة حدود ADM2 إذا كان المطلوب تحليل مناطق كل محافظة على الخريطة.
8. مراجعة API أمنيًا وتوحيد validation والاستجابات والأسماء.

## 15. قواعد يجب الحفاظ عليها

- لا إنشاء لحسابات العاملين من الواجهة العامة.
- تسجيل المريض من التطبيق يبقى فعالًا.
- لا migrations على قاعدة XAMPP الفعلية.
- كل إحصائية في لوحة الطبيب يجب أن تخص الطبيب فقط.
- المدير والسكرتارية يحصلان على إحصائيات تشغيلية شاملة، مع حصر إدارة النظام والإعلانات الحساسة بالمدير.
- الطبيب وحده يكتب التشخيص والبيانات السريرية لمريض مرتبط به.
- عدم عرض أرقام صغيرة قد تكشف هوية المرضى في التحليلات الجغرافية.
- عدم إعادة صفحات القالب التجريبية إلى القائمة الرئيسية.
